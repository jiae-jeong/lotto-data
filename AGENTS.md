# Lotto Research Execution Rules — Mandatory

This file is a mandatory execution layer for all future lotto study/research work in this repository. It supplements `LOTTO_PROJECT_PROTOCOL.md`. If an older clause can be read as permitting work to stop at a blocker, this file overrides that interpretation.

## 1. Core outcome rule

A daily study is not complete merely because a script was attempted, a blocker was documented, old results were rerun, or files were saved.

A valid daily study must produce at least one **new research contribution** relative to the latest repository state, such as:
- a newly registered hypothesis;
- a new cutoff-safe validation of an untested hypothesis;
- a new failure/error decomposition;
- a new model-comparison result that answers a question not already answered;
- a new prospective/untouched test design frozen before future outcomes;
- a new implementation correction that is independently versioned and tested;
- a new regime/model-selection/ensemble/calibration/diversification test;
- a new conclusion that changes the status of a hypothesis/model based on new evidence.

Routine refreshes after a new draw may be performed, but they are **maintenance**, not the day's new study contribution.

## 2. Anti-repetition gate — mandatory before computation

Before starting the day's analysis:
1. Read the latest `main`, the protocol, recent daily reports, hypothesis/failure registries, model results, and the most recent research queue/state.
2. Create a short inventory of what was already completed.
3. Compare the proposed work against at least the recent completed research.
4. If the proposed work is materially the same question, same model, same metric, and same dataset state as completed work, **do not rerun it as the main study**.
5. A rerun is allowed only when there is a concrete reason such as a new draw, code correction, changed frozen specification, reproducibility audit, or explicit regression check. Even then, label it `MAINTENANCE/RECHECK`, not `NEW STUDY`.
6. After maintenance, continue to a genuinely new research task in the same run.

The following already-completed work must not be used as the main daily study again without a new reason:
- B v1 reproduction;
- large Monte Carlo uniform-random baseline already established;
- H001 recent-vs-long frequency direction test;
- H002 due/anti-due gap-only test;
- prior pair/triple multiple-comparison tests;
- already completed pair/triple relation walk-forward;
- repeated descriptive 10/30/50/100 frequency tables by themselves;
- repeated generic odd/even, low/high, sum, consecutive-number summaries by themselves.

## 3. Blocker recovery ladder — stopping at "could not do it" is prohibited

A blocker is a routing event, not a daily result. When a planned path fails, immediately continue through the ladder below without waiting for the user to invent the workaround.

### Execution-path fallback
1. Diagnose the failed path briefly.
2. Try a different executable path: repository-preserved script, GitHub Actions, available Python runtime, reproducible standalone script, or another available execution environment.
3. If the exact executable cannot run, perform source/static validation where useful and move to an independent executable research task.

### Data-path fallback
1. Official/primary data source.
2. Repository-verified snapshot.
3. Secondary reliable dataset/API/source with cross-check.
4. Reconstruction from multiple sources if necessary.
5. Preserve provenance and do not pretend partial data are complete.

### Missing-source/model fallback
If a historical integrated source/model cannot be verified:
1. Do not invent or reconstruct it from memory or post-draw outcomes.
2. Preserve its status as `NOT FOUND/NOT ACCESSIBLE` in the registry.
3. Do **not** end the day's study there.
4. Select another independent research gap and execute it.
5. If a replacement model is scientifically useful, freeze a **new version/specification before evaluation** and test it as a new hypothesis rather than pretending it is the missing legacy model.

### Final fallback
If every route for one planned task is blocked, switch to the highest-priority independent task in the research queue and finish that instead.

A report whose main result is only `NOT EXECUTED`, `NOT FOUND`, an environment error, or a blocker explanation is an invalid daily study report.

## 4. Daily novelty requirement

Every daily study must explicitly separate:
- `MAINTENANCE/RECHECK`: refreshed or reproduced prior work;
- `NEW STUDY`: work answering a research question not already settled;
- `NEW FINDING`: what changed in our understanding;
- `NEXT TEST`: the next unresolved question generated by today's work.

At least one substantial `NEW STUDY` item is mandatory. If no new draw exists, novelty must come from a new hypothesis, new validation design, new error analysis, or new model architecture — not from rerunning the same statistics.

## 5. Research-priority queue to prevent repetitive study

Unless already completed later in `main`, prioritize unresolved work in approximately this order:
1. **Regime detection:** test whether model performance regimes can be identified using only information available before each target draw.
2. **Dynamic model selection:** select among frozen component models at each historical cutoff using only trailing pre-target performance, then nested walk-forward against static/random baselines.
3. **3+/4+ objective research:** distinguish models that merely raise 2+ hit rate from models that improve the high-hit tail; evaluate 3+/4+ with uncertainty and multiplicity control.
4. **Ensemble de-correlation:** test whether equal-weight combination dilutes useful signals; measure component prediction overlap/correlation and compare pre-frozen weighting schemes.
5. **Triple recent-strength falsification:** test whether recent triple performance is predictable ex ante or is a short-window fluctuation.
6. **H005_FIX structure-to-number mapping:** design and freeze a corrected mapping before evaluating it; keep it separate from legacy S008.
7. **Prospective untouched validation:** freeze rules for future rounds and preserve pre-draw artifacts for later evaluation.
8. **Recommendation failure decomposition:** connect actual purchased-line misses to signal selection/exclusion and test whether those failure causes recur historically.
9. **Candidate-bank / 3-line portfolio optimization:** evaluate whether three lines can improve joint 2+/3+/4+ coverage without merely increasing redundant overlap.
10. **Calibration and uncertainty:** quantify confidence intervals/bootstraps or exact tests where appropriate instead of relying only on point estimates.

Do not repeat an item once its specific research question has been answered unless new data or a new pre-specified question justifies it. Move down the queue or create a new independent hypothesis from the failure registry.

## 6. Model-development discipline

- All target-round predictions must be cutoff-safe: target `t` may use only information available through `t-1`.
- Hyperparameter/model selection must not look at the same holdout used for evaluation. Use nested walk-forward or a separately frozen validation design where needed.
- Do not promote a model because it looks best in the most recent window after seeing that window.
- Distinguish exploration from confirmation.
- Use multiple-comparison correction when many hypotheses are screened.
- Keep exact formulas, variables, weights, seeds, cutoffs, version names, inclusion/exclusion rules, and code paths reproducible.
- Never rewrite historical recommendations after seeing the draw.

## 7. Reporting rule to the user

The user-facing answer must lead with **what was studied and learned**, not with where files were saved.

Required order:
1. Today's genuinely new research question.
2. What was actually executed.
3. Key numerical results.
4. Interpretation: what is strengthened, weakened, rejected, or still uncertain.
5. How it changes the project/model/research direction.
6. Maintenance/rechecks, if any.
7. Blockers only as a short appendix together with the workaround taken.

Do not make a blocker the headline or conclusion. Do not stop the answer at “couldn't run”, “couldn't find”, or equivalent. If one task is blocked, report the alternative completed study instead.

Saving/committing is not itself a study result. A Git commit is evidence/preservation only; it must never replace the substantive study report.

## 8. Completion gate

Before saying the day's study is complete, all must be true:
- [ ] latest repository state was read;
- [ ] completed/repeated topics were identified;
- [ ] the main study was not merely a duplicate of prior work;
- [ ] at least one new research question was actually tested or materially advanced;
- [ ] cutoff/data leakage rules were respected;
- [ ] results were compared with an appropriate baseline;
- [ ] failures were routed through alternate paths instead of ending the study;
- [ ] the user-facing response contains substantive findings, not only storage/status information;
- [ ] outputs preserve enough detail to continue tomorrow without starting over.

If this gate is not yet satisfied, continue working on another valid research task rather than ending with a failure/status-only report.
